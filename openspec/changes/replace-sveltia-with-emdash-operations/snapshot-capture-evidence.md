# Published snapshot capture preparation

`scripts/capture-cms-snapshot.mjs` captures the complete inventory of the thirteen configured editorial collections through bounded reader callbacks, resolves each published record's pinned live revision, and rechecks the complete inventory before returning canonical JSON and its SHA-256 digest. Current editable row data and draft revision pointers never enter the returned snapshot.

The inventory includes record IDs, slugs, status, version, and live/draft revision pointers. Capture rejects changed vectors, incomplete totals, duplicate records, repeated/empty pagination, incorrect revision ownership, missing published revisions, and exhausted request budgets. The default total budget is 200 reads; the function does not automatically retry. Readers must enumerate the complete unfiltered collection inventory. The installed native CMS handlers and revision schema were inspected to establish these field and identity contracts.

Local Node tests cover a published record with later private draft data, deterministic output, changed versions, deletion between scans, incorrect revision ownership, incomplete totals, repeated cursors, and budget exhaustion. They are included in the root contract test command.

The REST reader now uses the exact configured environment hostname (or approved Local loopback ports), fixed content/revision GET routes, native supported creation-order pagination, Access-only credential forwarding, redirect rejection, a 30-second timeout, and a 4 MiB response cap. It makes no automatic retries. The CMS runtime permits authenticated GET of an exact revision ID; restore and alternate writers remain blocked. Native terminal pages may omit `nextCursor`, which capture normalizes to the end of pagination while retaining total-count checks.

An isolated compiled-CMS smoke publishes Artist and Release records, saves newer drafts, and runs the actual REST reader/capture against native CMS responses. Exactly the published records are exported and the later draft marker is absent. Exact revision GET works, restore remains 404, and all thirteen collection validation scenarios still pass. The smoke uses `persist: false` and Local bindings; it does not affect the user's persistent Local stores.

Capture also rejects duplicate published collection/slug paths and requires every pinned Release Artist reference to resolve to an Artist included in the published snapshot. Local regression checks cover draft, scheduled, archived, and missing Artists, duplicate slugs, and a newer editable reference differing from the pinned live reference.

Referenced media is now captured through fixed authenticated media metadata/file routes. The capture deduplicates media IDs (including native expanded local image objects and Portable Text references), checks ready status, identity, size, stored SHA-1, permitted raster bytes, filename/type agreement, and original dimensions using the existing upload validator. The snapshot contains a SHA-256 media manifest and the result retains exact bytes keyed by SHA-256 for subsequent immutable storage. Unreferenced draft images are not fetched. File reads are capped at 20 MiB, total media at 256 MiB (caller may lower it), and both metadata/download requests share the total request budget. Unsafe storage paths and redirects are rejected before credentials can reach another origin. The final inventory recheck follows media reads, detecting content changes made during downloads.

Each pinned revision now passes the existing editorial content schemas before media is downloaded. A revision-only validator recognizes the installed CMS's enriched local image shape with strict metadata types; direct editorial write validation remains unchanged. Invalid dates, missing required fields/alt text, unsafe rich text, external media, and unexpected editorial or media metadata fail capture. The original revision data remains intact; validation does not silently remove fields from the snapshot. Collection enumeration now comes from the shared CMS collection map.

The private R2 object writer is prepared in `apps/backend/src/cms/snapshot-storage.ts`. It derives keys from environment, object kind, and SHA-256, bounds manifest/media objects at 4/20 MiB, and owns a copy of the bytes while hashing/writing. Existing matching objects need only one HEAD read; absent objects use a conditional PUT with a native SHA-256 integrity check. A concurrent winner is verified, not overwritten. Corrupt existing objects and lost acknowledgements stop the attempt; a caller's later retry reuses a verified existing object without another write. This follows the [R2 conditional-write and checksum API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/). Snapshot, backup, and draft storage prefixes are rejected by the generic CMS media route, including encoded paths.

The writer now exposes media storage separately from manifest completion. `completeSnapshot` validates the bounded manifest, target, editorial records, published Artist references, exact referenced media inventory, byte budget, and stored image bytes/dimensions before writing the manifest as a completion marker. It reads each unique media hash once and keeps only one original object in memory at a time. Arbitrary raw manifest writes are no longer exported. It creates no live pointer; publication dispatch and deployed-state acknowledgement remain separate. The R2 test binding is isolated and local only; no deployed binding or resource was changed.
