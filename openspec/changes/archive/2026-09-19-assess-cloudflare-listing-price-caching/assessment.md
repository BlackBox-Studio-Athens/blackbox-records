## Demand and savings limits

Before the pilot, existing Observability over the preceding 24 hours returned 23 successful events matching `listing`, no errors. Visible rows included six UAT and one PRD top-level listing GETs, matching DO/log events and trace records. **23 events is not 23 shopper activations.** UAT activity clustered around the previous release; user/bot attribution, complete unique request count, repeat-browser rate, geographic demand and price-update frequency remain unknown. The later staff `workspace` search returned 112 successful events and zero errors; it likewise is not a unique staff-read count or per-page demand measurement.

For N listing activations, H valid cache hits and S snapshot rows, the current path costs approximately N scans of S rows. An appropriately placed cache could avoid H scans; fills remain N−H and every invalidation/revalidation has a cost. At this catalog size each avoided scan is approximately 107 rows and each browser/304 body avoidance is at most 11,093 decoded bytes. With zero useful hits the saving is zero and cache lookup/fill work is added. The pilot's four repeat requests are deliberately synthetic, not an observed 80% shopper hit rate. No traffic extrapolation from purchase counts is used.

Cloudflare's [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) is local to a data center, lacks tiered `put`, global `delete`, and `stale-while-revalidate`/`stale-if-error` support. [Workers Cache](https://developers.cloudflare.com/workers/cache/) is a separate mechanism with different routing and charging; [configuration](https://developers.cloudflare.com/workers/cache/configuration/) and [keys](https://developers.cloudflare.com/workers/cache/cache-keys/) require explicit review before selection. Zone Cache Rules and headers alone do not establish a Worker-generated cache hit. No commerce route is added to Pages or the renderer.

Any future public cache must isolate environment, hostname, representation version, relevant query parameters and CORS origins; apply CORS per request or partition correctly. Bypass authorization/cookies, reject `Set-Cookie` and non-success/private responses, and keep preflight separate. Failed refreshes must not silently extend an unapproved stale window. Origin/quota failures retain the current unavailable state unless a different policy is explicitly agreed. Rollback must stop reads from the cache and account for surviving browser entries; Workers Cache disablement alone does not purge entries before re-enabling.

`apps/staff/src/lib/staff-query.ts` already owns a document-local TanStack Query client: configured 30-second freshness, five-minute inactive retention, retries disabled. `readStaffQuery` overrides freshness to zero; it can share concurrent work but does not intentionally reuse a completed fresh payload for later explicit reads. `useStaffRead` caches a success marker for focus/online/visibility refresh suppression, not the whole component's response; intervals invalidate that marker before refresh. Hidden/offline refreshes pause. These are existing values, **not newly approved TTLs**. Do not turn the marker cache into persistent private-data storage. See [TanStack defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults) and [invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation).

Staff client-state reuse must account for logout, identity/role changes, access expiry and cross-tab edits, with fresh authorization and revalidation before actions. Caching upstream of origin authorization can skip those checks. Current Access Cache API restrictions further rule out treating protected staff hosts as equivalent to the public listing host. Any staff runtime change also requires staff/editor acceptance and applicable publication/privacy checks.

## Decision and verification

Proposed discussion outcome: keep listing and mutable staff responses `no-store`. If optimization is desired, first measure repeated hashed-asset transfer and accepted-manifest reads, then consider only those two staff candidates. No nonzero freshness window is justified by this evidence; no window is proposed or approved. The first listing delay merits a cold/warm runtime investigation if it recurs in real browsing, rather than being labelled a cache problem.

Assessment-stage checks: OpenSpec guard; 11 existing listing-reader/repository Worker tests; 27 existing public-commerce route tests; one existing staff workspace pagination test; local diagnostic assertions; strict OpenSpec and targeted Markdown formatting. Runtime code was unchanged during that stage. The subsequent decision and implementation checks are recorded at the top of this report. No archive or deployment was performed.
