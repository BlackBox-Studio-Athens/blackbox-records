# Design

## Context

See [proposal.md](proposal.md) for the requested scope. Nx projects and their native boundary metadata identify ownership. The public frontend has 11 closed modules, with `web-layouts` and `web-pages` composing them. The user also confirmed both shared packages and the 14 commerce backend modules. Nested roots are excluded from their parent module's review. Existing specs and observed source behavior remain the acceptance contract.

## Goals / Non-Goals

**Goals:** Mostly remove proven dead, redundant, duplicated or unnecessary production code and test scaffolding through concrete, independently reviewed refactor slices. Preserve one-to-one functionality and meaningful regression evidence. Report production/test reductions and net files/lines separately, excluding formatting and required audit Markdown; impose no deletion quota.

**Non-Goals:** Product or visual design changes, unrelated bug fixes, module-boundary redesign, dependency adoption, staff/CMS implementation cleanup, generated code or migration changes, content changes, commits, release or hosted mutations.

## Decisions

1. **Run individually fresh review/implementation roles with coordinated concurrency.** Each module retains separate fresh review/implementation roles. All remaining turns use `gpt-6.1-sol` and `high` reasoning, with Full access (`danger-full-access`, approval policy `never`) explicitly requested by the user. A reviewer returns findings without edits; a different fresh implementer independently verifies them before changing code. The user clarified that one-by-one means thorough individual module coverage and does not limit thread concurrency. Use four concurrent read-only reviewers and dependency-aware execution by up to four disjoint source writers; handle source dependencies before consumers, since disjoint roots alone are insufficient. Preserve module pair identities and adopt the exact fresh roles without duplication. Future fresh implementers may prepare read-only without files or checks, then resume those SAME roles independently while acceptance is pending through the parent's explicit `--execute --defer-acceptance` action construction. This bypasses only preceding checkpoint checked-task requirements; default execution remains strict, and actual completed preparation, full raw report equality, high/Full access/never profile, separate fresh roles, ownership, reservation and duplicate-execution checks remain in force. Recheck current owned/caller hashes before edits. Execution prompts reference immutable verified full review/prep paths, IDs and hashes instead of replaying their text; prepare mode retains full review delivery, and implementers still save the complete received review to its canonical record. These preparations and execution releases do not establish acceptance. The parent only orchestrates handoffs and owns starts; no new persistent task database or overlapping daemon is added. The prior high controller exited blocked; no restart is authorized. Reuse all 29 completed full reviews, including refreshed modules 12-15, five accepted implementations and verifier retry02 acceptance. Preserve historical max settings and role IDs; the deliberately interrupted module 5/17 implementers resume the same roles at high effort. Reuse retained instructions, whole-module inspections, both-graph evidence, probes and checks only for byte-identical covered source hashes; inspect all changed owned deltas and current finding callers/tests, retaining full module verification. One exclusive persistent verifier owns shared task markers, source binding, graph refresh coordination and acceptance evidence while source writers are idle. The initial app-created reviewer imposed workspace-write and was archived; replacements use explicit app-server permission settings.
2. **Use the saved Ponytail instructions.** The archived 5.0.0 review and coding skill sources provide the requested review method without restoring or enabling the plugin. Every finding needs concrete source/caller evidence; shorter code alone does not justify an edit.
3. **Preserve all observable behavior.** This includes HTML and visible copy, styling and motion, focus and accessibility, URL/history semantics, persistent player and cart state, async timing and cleanup, ordering, validation, error behavior and exported contracts. Uncertain equivalence rejects a candidate until evidence resolves it.
4. **Prefer deletion and existing primitives.** Remove dead code, redundant layers and proven duplication; use native/platform features and existing helpers where equivalent. Split by distinct responsibility only when it reduces real complexity. Add an abstraction only when the result clearly has less code and less complexity. Preserve exact behavior rather than forcing a reduction.
5. **Keep valuable tests.** Remove or consolidate a test only when another retained check covers its distinct behavior or it merely freezes implementation structure. Retain security, parser, money, persistence, lifecycle and edge-case coverage. Add tests only for an actual evidence gap introduced by a selected refactor.
6. **Use exclusive, source-bound, proportional acceptance verification.** Each implementation immediately runs its own published scoped module/file tests and focused lint/type checks, recording checks and exclusions. The persistent verifier consolidates source-bound shared checks and the required e2e/browser/normal Local union selected by the repository matrix on the final stable tree, with all source writers idle. Both graphs, exact equivalence, security and meaningful coverage obligations remain required. Refresh Graphify once after a meaningful stable code batch while implementers are idle, or reuse a recorded refresh only when its actual relevant source fingerprints still match. Implementation threads do not race on graph output, shared task state, formatting or shared Local acceptance. Reuse passing checks only for unchanged actual covered input bytes. Module task acceptance remains unchecked until its required evidence genuinely passes; task wording about evidence before advancing governs acceptance, while explicit deferred execution permits independent implementation. Intermediate checkpoint acceptance remains valid when its actual gates pass; retain old failures and never fabricate passes. Unrelated code outside the assigned modules and acceptance dependencies does not by itself invalidate scoped module completion; record its exact changed paths and retain final-tree gaps. Intermediate global validation is optional scheduling evidence. Never infer browser/provider/release acceptance from unit checks or historical global validation.
7. **Keep one task record and preserve audit evidence.** `tasks.md` is the only persistent task state. Reports live under `reviews/<module>.md` and `implementations/<module>.md` in this change, including thread IDs, accepted/rejected findings, changes, meaningful test deletions, evidence and gaps. The verifier may normalize formatting only in audit Markdown while implementers are idle, preserving complete content, IDs, identities, source hashes and evidence links; substantive corrections return to the owner. Immutable raw JSON and earlier failed attempts remain unchanged. Final evidence lives in `validation.md`; transient logs use `.codex-artifacts`.
8. **Keep mandatory final integration gates.** Task 30.1 owns one normal policy-compliant `pnpm validate` on the final combined tree, with matching actual before/after inputs and its canonical summary. Task 30.2 owns strict OpenSpec final validation and the complete record of all 29 pairs and acceptance gaps. Strictly validate the change after checkpoint notes/task updates too. An intermediate pass does not establish final-tree acceptance, and neither final task becomes complete until its actual requirements pass. No maintainer grant, full-run bypass or weakened module task definition is authorized.

## Risks / Trade-offs

- Subtle behavior may depend on defensive checks or async lifecycle machinery. Preserve those unless callers, source and relevant tests establish equivalence.
- Shared helpers can affect later modules. Check connected consumers and run affected validation; fresh later reviews inspect the resulting tree.
- Runtime and source-inspection tests serve different purposes. Record a deletion's lost and retained coverage instead of deleting by test count or assertion style alone.
- The modules differ greatly in size. Review thoroughly without a finding quota, time-box that hides gaps, or a target number of deleted lines.

## Migration Plan

No data or deployment migration is required. Review each module diff as a local refactor slice. If equivalence fails, restore the affected slice while preserving unrelated work. Promotion is outside this change.
