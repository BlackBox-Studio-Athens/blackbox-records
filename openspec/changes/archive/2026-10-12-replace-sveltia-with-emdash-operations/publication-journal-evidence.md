# Publication journal preparation

Task 8.1 now has an application-owned `_blackbox_publications` journal, with its additive migration under `apps/backend/cms-migrations/`. It belongs to CMS D1, separate from EmDash core tables and the commerce migration history. Only isolated test databases receive this migration during verification; deployed and persistent Local databases remain unchanged.

`requestPublication` validates the request identity, environment, verified actor, and requested native revision identity, then durably inserts a pending record. Concurrent/repeated submissions preserve the original timestamp and state. Reusing the request identity with a different actor, target, or revision fails without changing the retained record. `readPublication` scopes reads to the requested environment. The repository cannot mark a request Live; the SQL constraint additionally requires snapshot, code, CI run, and deployment identities before Live is possible.

Native D1 tests cover concurrent replay, reads from a later caller, changed-input conflicts, environment isolation, malformed requests, and rejection of Live without deployment evidence. They also verify that the publication table was not created in `COMMERCE_DB`.

The combined CMS handler now routes `POST /_emdash/api/blackbox/publications` and `GET /_emdash/api/blackbox/publications/{id}` after existing hostname/Access authentication. New requests require member-or-owner role, exact Origin, the CMS CSRF header, bounded JSON, and only the client request/revision IDs. Actor and environment come from verified server context. Two supported native CMS reads confirm the revision identity and its owning entry's current published/live-revision state before a pending record is created. Replay reads the retained request first, so later edits or a temporary CMS failure cannot turn a successful request into a duplicate. The response exposes only request ID, pending/live/failed status, and request time, with private/no-store caching.

Endpoint tests use isolated D1 plus native-shaped CMS responses. They cover replay, later status reads, actor/target isolation, denied role/CSRF, injected server fields, oversized requests, forged completion paths, draft/stale/foreign revisions, throttled CMS reads without retries, and unapplied application migrations. The real compiled CMS smoke verifies that an unapplied journal migration returns a sanitized 503 and does not bootstrap application tables.

Dispatch persistence now has an additive `0002_publication_dispatch.sql` migration. An atomic D1 update claims only the latest inserted request for one target and imposes a five-minute lease/cooldown. Concurrent callers cannot claim it twice; a failed or unacknowledged dispatch leaves the request pending and retryable after expiry. Each retry replaces its attempt token. CI run binding requires the current token and unexpired lease, permits exact replay of the retained run, and rejects another run or environment. These helpers are server-only; the token is not workflow authentication and is not exposed in staff status responses.

Isolated D1 tests cover concurrent dispatch and competing CI claims, lease boundaries, stale attempts, wrong targets, malformed run IDs, retained pending state, and latest-request selection. Finishing the latest request does not dispatch an older waiting revision. Older requests remain pending until the planned completion/supersession reconciliation is implemented. The compiled CMS now routes the exact `POST /_emdash/api/blackbox/publications/run` endpoint to a separate machine credential check. `CMS_PUBLICATION_EXPORT_TOKEN` is a target-specific Worker secret containing 32 random bytes encoded as 64 lowercase hexadecimal characters. It has no committed/default value; only isolated tests configure a fake value. The handler compares the Bearer credential with `timingSafeEqual`, requires the configured HTTPS CMS hostname for hosted environments (loopback for Local), and accepts only a bounded `{id, dispatchToken, ciRunId}` body. The environment comes from Worker bindings. Staff cookies and the dispatch token alone cannot authorize it.

This credential currently permits only CI run binding; it does not authorize general CMS/editorial writes, commerce routes, or completion. The target-scoped workflow credential now also permits private snapshot staging through exact `PUT /_emdash/api/blackbox/publications/media` and `/snapshot` endpoints. Both require `X-Publication-ID` and `X-CI-Run-ID` matching a pending journal record already claimed by CI. Media uses bounded raw octet-stream bytes (20 MiB); the manifest uses bounded UTF-8 JSON (4 MiB). No general CMS, commerce, or completion authority is added.

The manifest must contain the publication's requested revision and pass the existing complete content/reference/image validation against media already stored in the same target. Only then is its immutable R2 manifest hash conditionally bound to that publication/run. Exact replay is write-free; a different manifest cannot replace the first accepted hash. A race can leave an unbound private immutable object, but cannot replace the accepted snapshot or mark Live. Media staging is closed once a manifest is bound. Invalid or incomplete manifests fail closed and leave the request pending. Snapshot loading, approved-code binding, deployment completion, and supersession reconciliation remain open.
