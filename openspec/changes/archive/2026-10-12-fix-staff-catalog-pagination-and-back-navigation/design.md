# Design

## Context

See [proposal.md](proposal.md) for motivation and [the delta spec](specs/staff-workspace/spec.md) for the behavior contract. The user confirmed that navigation work covers the whole staff workspace. This follow-up extends `staff-workspace`; it does not replace or mark complete the outstanding gates in `redesign-staff-workspace`.

### EmDash reuse assessment

The repository and installed packages pin `emdash` and `@emdash-cms/admin` to **0.38.0**. The installed admin declarations expose `FindManyResult<T>` with `items`, optional `nextCursor`, and optional `total`; its full `ContentList` supports `hasMore`, `onLoadMore`, server search, and controlled sorting. The inspected package declarations do not expose a standalone catalog pager.

EmDash's [query guide](https://docs.emdashcms.com/guides/querying-content/) documents native cursor pagination and a stable content-ID tie-breaker. That public collection API is reference material; the existing protected workspace must continue using its staff runtime API and draft visibility, not switch to public published-only reads. Installed 0.38.0 types and local native-runtime tests are the compatibility authority if newer online examples differ.

Reusing the entire native admin `ContentList` would also import its routing, content-status, trash, and action model into the custom staff experience. Its props do not provide the existing BlackBox item/editor/commerce workflow as a drop-in replacement. The smaller change is to retain the current list, existing Button components, and EmDash-backed adapter. Do not copy vendor pagination internals, deep-import unexported components, mount a second admin, or upgrade dependencies for this repair.

## Goals / Non-Goals

**Goals:** Make batch traversal and returning to work obvious, preserve state across same-document and full-document staff navigation, and ensure navigation cannot lose work or execute business actions. Keep one source of list truth: the protected service plus the current URL, with lightweight per-entry navigation metadata.

**Non-Goals:** A new visual identity, public-site navigation, search/taxonomy changes, a router migration, infinite scrolling, numbered page jumps, page-size settings, whole-catalog downloads, new count queries, new CMS tables, or changes to publication/commerce permissions. Existing image-picker pagination can remain load-more; only its task return behavior is in scope.

## Decisions

### 1. Keep explicit 25-entry pages and make the controls visible

Put a compact pager below the list search/filter toolbar and repeat it after the rows. Keep Previous and Next side by side, with existing staff button styling and at least 44 px touch height. Give the two navigation regions distinct accessible labels, such as Catalog pages, top and Catalog pages, bottom. Use one presentational pager implementation for these two placements, without a generic data-table framework.

Display `Page 2 · 25 items on this page` when the visited cursor trail establishes the ordinal. On a copied later-page URL with no known trail, display `25 items on this page` and a First page action; disable Previous until an actual predecessor is known. Omit `of N` and any total inferred from page length. Keep controls available on the final page to allow a return; an unpaginated one-page result does not need duplicate disabled pagers. Empty results display a reset-filters action.

After a successful explicit Next/Previous, scroll the actual list scroll container to its heading and focus that heading with `tabIndex=-1`. Use the existing live-status pattern to announce the position. A detail return instead restores the prior list position and originating row. Background refresh does neither. No smooth motion is required. This addresses both the buried pager and the observed arrival at the bottom of a new batch.

**Alternatives considered:** Raising the limit only hides the problem; Load more/infinite scrolling grows the DOM and complicates exact returns; a numbered pager requires counts and arbitrary seeking absent from the current cursor contract. A sticky overlay pager adds overlap/focus risks. Two ordinary pager placements are enough.

### 2. Treat page loads as transactions

In `ContentApp`, separate the requested browse state from the last successfully displayed state. Keep `readStaffQuery` and its document-owned, non-persistent cache. Include collection, normalized search/area/format/sort, and the opaque cursor in the request identity. Preserve native server filtering before pagination and include editorial-only records.

Only the newest successful request commits rows, continuation, current cursor, visited cursor trail, URL, and position summary together. `catch` and `finally` must also be generation-checked so an older request cannot clear a newer loading state or replace its error. Disable duplicate paging while pending. A failed page leaves the previous successful page intact and retains a retry target; access denial uses the existing protected-data clearing behavior.

Changing criteria resets the requested cursor/trail. While that request is pending, do not label retained rows as results of the new criteria; show pending feedback. On failure retain the previous committed URL and results with a retry for the chosen criteria. An explicit retry creates no duplicate successful navigation entry. Cancellation or ignored stale results must cover the complete request lifecycle, not just `setItems`.

Treat cursors as opaque. Never calculate offsets, decode a cursor in staff code, or use client-side filtering of the first page as a substitute. An absent continuation means the end; an exact 25-row page is not proof of more results. Repeated/rejected cursors stop with a recovery action. If a catalog edit leaves the current page empty, keep its criteria and offer First page rather than silently relabeling it or looping through requests.

Each intentional catalog page request uses the existing bounded projection. Do not prefetch the whole catalog, add background page crawling, add count polling, or fetch editorial content once per row. Retain existing publication checks and thumbnail budgets.

### 3. Use native browser history as the navigation record

The URL remains authoritative for addressable browse state: existing collection/view, `q`, area, format, sort, cursor, record/variant/order identity, and meaningful tab state. Parse and normalize it through a small shared staff utility where more than one surface needs the same behavior. Do not forward UI-only return metadata into the strict workspace API query.

Use `pushState` for a successful explicit Next/Previous transition or opening a new task/detail. Replace the current entry for debounced typing/filter refinement, tab refinement within the same task, canonicalization, and automatic refresh. Before leaving, preserve that entry's cursor trail, stable focused-row identity, relevant scroll-container position, and contextual return target in a namespaced part of `history.state`, merging unrelated existing fields. Restore these together on `popstate` and initial mount; restoration must not push another entry or trigger the filter-reset effect.

The state must identify the known originating history entry, not merely inspect `history.length`. For same-document detail returns, navigate back to that known entry; do not push a duplicate list entry. Keep tab refinements within the current task entry so Back returns to the task's origin. Where the origin cannot be proven to be in the current history chain, follow the validated named parent with replacement navigation. Do not infer a trusted origin from `document.referrer`.

For ordinary full-document staff links, carry one validated `returnTo` path/query in the destination URL, plus a single same-tab navigation handoff for the source entry identity when available. The handoff is scoped to the exact destination and consumed once; it contains navigation metadata only. The destination stores that origin in its own history entry. Strip nested `returnTo` values to avoid recursive URLs; navigating back to the real source history entry restores that entry's own origin. If session storage or history-state writes fail, retain working explicit parent links and addressable current-page loading, without claiming an unknown predecessor.

Validate history/session/URL metadata as untrusted input. Accept only same-origin recognized staff paths, the existing route-specific query keys and bounds, and valid collection/tab values. Reject external or protocol-relative targets, credentials, API/auth endpoints, unsupported paths, and malformed or oversized state. Resolve labels from the recognized destination; never accept arbitrary supplied labels or navigation code. Store only the route's existing navigation criteria and identifiers, not content bodies, customer/order payloads, stock authority, or credentials. Do not introduce a persistent content cache or a second navigation stack.

**Alternatives considered:** Bare `history.back()` can leave the workspace after a direct external visit; fixed parent links lose filters and review context; a new client router would require migrating all staff islands and guards. A small utility around native history and links is sufficient.

### 4. Give every staff task one clear return action

Use an arrow plus visible `Back to <destination>` text, positioned immediately before or beside the task heading. Prefer the current component's existing action; let `StaffShell` provide the consistent root fallback without also rendering a duplicate task-level Back button. Existing root navigation stays available. Overview needs no redundant Back to Overview.

In a creation flow, label the local previous-step action clearly, such as Back to details; the task-level Back to Distro & merch leaves the flow. Existing review selection and pending publication identities survive a return. Do not change native admin destinations or auth screens.

### 5. Leave protection belongs to the existing task owner

All new Back paths must pass through the current task's save/leave behavior before navigation. Reuse `useDraftAutosave.flush`, ContentApp conflict/reload handling, ItemSetup recovery, and Stock's `protectInput`; do not add a competing generic confirmation framework. Avoid duplicate handling by the shared helper and existing capture-phase anchor guards.

For same-document browser Back/Forward, retain the current location and task snapshot until the leave guard settles. If it refuses, restore the current history position with a one-shot suppression of the compensating history event; keep URL and visible task aligned and focus the existing recovery UI. On success, apply the requested state exactly once. A second navigation while the guard is pending must not produce repeated saves, duplicate pushes, or two dialogs. Native full-document browser traversal retains `beforeunload` protection; do not promise that an asynchronous save can block browser unload indefinitely.

Stock adjustments, counts, price setup, and publication operations retain their current explicit confirmation and recovery identities. Back never submits them or clears an uncertain result. Recovery checks remain available after returning. Ordinary clean navigation asks for no confirmation.

### 6. Extend the existing tests at the actual failure boundaries

Use the current Vitest suites and `scripts/test-content-workspace.mjs`; add no test framework. The first regression must fail against the current UI because Next is below the initial viewport and the next batch retains bottom scroll. Assert bounding rectangles/scroll positions and focused elements, not merely that Playwright can locate and click a control. Scope duplicated Next/Previous locators to the named top/bottom pager.

## Risks / Trade-offs

- **Mutable ordering:** Editing a title or recently edited entry can move it between pages. Native cursor order governs the next read; refresh/recovery must be honest. Full exact-once traversal is asserted on a fixed dataset, not claimed as snapshot isolation while other members edit.
- **History interactions:** The shell, content app, orders, and stock currently write history separately. One namespaced metadata shape and explicit ownership avoid clobbering each other's state; tests must cover returning between these islands and canceled popstate events.
- **Unknown deep-link predecessor:** EmDash supplies a forward cursor, not an arbitrary previous-page lookup. A copied URL without history gets First page and Next, not a fabricated Previous target or page number.
- **Optional browser storage:** Navigation metadata is convenience state. Failures degrade to validated parent links; draft/operation recovery follows its existing stronger protections and must not be downgraded.
- **Native component mismatch:** Replacing the full staff list with EmDash's admin list would expand this repair and change workflows. Reuse its supported runtime queries and current staff primitives; revisit full admin adoption only as a separately scoped product change.
- **Hosted cost:** Do not add sessions, KV, polling, or a full catalog scan. Any later hosted acceptance requires the Free-tier preflight; the bounded diagnostic above is not account-usage or release evidence.

## Migration Plan

1. Add the focused failing regression and confirm the native cursor contract locally before changing behavior. Keep unrelated existing changes intact.
2. Repair the shared content pager and history transaction; add the small return-state utility and integrate the existing task controls across the surface matrix. Update the two staff guidance documents to describe actual behavior.
3. Run focused regressions, then `pnpm validate` and `pnpm validate:editor` against the final source fingerprint. Follow the relevant Local checks in `docs/content-workspace.md` and `docs/content-publication.md`: built staff browser fixtures in Chromium/Firefox, preview policy, and the real shared-template preview smoke for editor navigation/autosave regression. The canonical CMS build remains responsible for source/generated no-KV validation. Record results and any baseline failures; do not label partial checks as completion.
4. The implementation can be accepted locally after those gates. Hosted acceptance is a separate release step: preflight account-wide allowance, deploy the reviewed UAT candidate through the existing release workflow, and repeat a small read-only Distro Next/Previous/detail-return and staff Back check against that revision. PRD promotion requires its existing explicit release authorization; this plan authorizes no deployment or data mutation.
5. No migration, seed, new binding, or feature flag is required. Roll back through the existing code-release process to the prior staff/CMS artifact; native content, commerce state, and saved drafts remain intact. Optional `returnTo`/history metadata must be safe to ignore when older code runs.
