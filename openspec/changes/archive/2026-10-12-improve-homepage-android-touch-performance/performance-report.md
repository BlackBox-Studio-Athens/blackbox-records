# Android Messenger homepage performance implementation evidence

## Scope and comparison

This implementation addresses the two source findings in the approved review: repeated motto transition work and destination prefetch at the start of a touch/pen gesture. It retains native scrolling, the fixed hero composition, player persistence, responsive showcase media, lazy showcase validation, and the existing motion design. The July round-two Home LCP of 1.648 s and October round-three Home LCP of 1.472 s are historical context, not paired before/after measurements. October 9 mobile fixes were already on local main and remain absent from the PRD release checked in the review (`4bb78b4f`); this change does not promote PRD.

All paired runs used the same Windows host, Chromium 153.0.8010.12, production static Local preview at `http://127.0.0.1:4321/blackbox-records/`, a fresh mobile/touch context per run, 390×844 viewport, 150 ms RTT, 1.6 Mbps down, blocked third-party analytics, the same `touch-home-input` script and cadence, and three sequential runs per arm. The default arm used 4× CPU/DPR 2; the stress arm used 6× CPU/DPR 3. The populated state used one built candidate with a deterministic ready preorder listing-price response; the empty state returned no preorder listings. This fixture is not a claim about live PRD stock or content. Every successful raw file reports `treeUnchanged: true`; the baseline and post source hashes differ as expected, and each arm retains its own build hash. Calibration runs before the final harness were excluded because their menu readiness/diagnostic behavior differed.

At 4× CPU, the populated Home first traversal no longer has a long task in any of the three paired post runs. The separate [post-change Home idle traces](../../../.codex-artifacts/runtime-performance/2026-10-10-mobile-review/post-home-idle.json) contain zero long tasks across three five-second touch/4× observations; the previous review saw motto-enabled tasks of 59, 61, and 64 ms in its separate seven-second observations. The 6× post repeat outlier of 52 ms contains about 1 ms of `FunctionCall` and under 1 ms of `UpdateLayoutTree` in its raw trace, without motto construction or drawing work. This supports the narrow goal of removing repeatable motto-attributable 50 ms tasks; it does not establish a 6× zero-long-task budget for the entire page.

Early-load long tasks remain: maximum per populated 4× run was 211/163/235 ms before and 276/246/274 ms after. These occur during opening/hydration and are not attributed to the motto refactor. First-`scroll`-event latency and successful menu-tap time vary enough that no general tap or scrolling speedup is claimed. Menu opens were intermittent on **both** builds, including 1/3 in the 6× baseline and 2/3 in the 6× post runs. The profile retains failed taps with `menuOpened: false` and a null tap time rather than silently excluding them. A separate five-run [post-change event probe](../../../.codex-artifacts/runtime-performance/2026-10-10-mobile-review/probe-menu.json) reproduced four missed menu taps after the synthetic swipe: each had pointerdown and pointerup on the Menu button but no browser-dispatched `click`; the one successful tap had a click. In those misses the shell never received a navigation activation. This implicates the gesture sequence in the local browser emulation, without proving the cause on Messenger. Normal phone browser menu tests pass, but these lab observations and the reported Messenger delay remain open for same-device verification. Continuous scrolling is measured separately from tap timing; neither measure is field INP.

The corrected `mobile-load` context now sets `isMobile` and `hasTouch`. Three [post-change Home mobile-load runs](../../../.codex-artifacts/runtime-performance/2026-10-10-mobile-review/post-home-mobile-load.json) reported LCP 1.976/2.044/1.972 s and CLS 0/0/0 under 4× CPU and slow networking, within the mobile-stress LCP and CLS limits. This is a post-only check, not a comparison with July or October LCP values.

## Behavior and release checks

- A cancelled touch swipe on a Home news card produced no overlay-document request; a subsequent tap opened the overlay. The affected check passed in Chromium mobile and WebKit mobile (WebKit exercises the pointer/focus cancellation path because Playwright does not expose a WebKit touch-drag CDP API).
- The seven text slices and five waveform shards remained the same DOM nodes across word changes and a resize in both phone engines. Desktop checks passed for the word sequence, Home return, and reduced motion.
- Horizontal card swipes and Home return were covered by after-change browser regression checks, not by a separate three-run paired trace for those two paths. Their comparative latency remains unmeasured.
- `pnpm test:app-shell`, the affected Home swipe-row checks, shell navigation checks (13 passed on each mobile engine and 9 passed on Chromium desktop), `pnpm build:web`, and `pnpm validate` passed on the final source tree. Validation summaries are retained under `.codex-artifacts/validation/`. OpenSpec strict validation passed before implementation and at handoff.
- No hosted Worker load test, UAT deployment, PRD promotion, or physical Android Messenger run was made. The release acceptance step remains a same-phone Messenger/Chrome comparison against one identified UAT release with device model, Android version, Messenger/Chrome versions, swipe/tap observations, and release identity. Emulation does not close the original report.

## Local follow-up: cold input and Menu activation (10 October 2026)

This follow-up used the same production Local build (`d62bbb967245` build-hash prefix), Chromium 153.0.8010.12, 390×844/DPR 2, 4× CPU, 150 ms RTT and 1.6 Mbps down. All retained files report `treeUnchanged: true`. Source-hash prefixes differ across the diagnostic harness edits; each comparison below uses identical hashes in its own arms. The original `firstScrollMs` was a `scroll`-event timestamp, not a visible-frame measurement. The harness now reports `firstScrollEventMs` and the next animation-frame _callback_ separately; neither is field scroll latency or INP. [INP excludes scrolling](https://web.dev/articles/inp).

An initial diagnostic callback read `scrollY` during early `scroll` events. A trace showed that this read could force a full-document layout, so those calibration runs are excluded. The retained probe records passive event timestamps and frame-callback times without reading scroll position inside either callback. Its full event/trace data is in the linked JSON files.

Three fresh [populated](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/home-populated-clean.json) and three [empty](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/home-empty-clean.json) Home runs share source hash `6a57880707b8` and the same fixture/cadence within each state:

| State     | First `scroll` event (ms), runs | Largest early renderer task (ms), runs | Layout nested in those tasks (ms), runs | Settled first/repeat ≥50 ms tasks |
| --------- | ------------------------------- | -------------------------------------- | --------------------------------------- | --------------------------------- |
| Populated | 54, 316, 331                    | 338, 245, 258                          | 331, 231, 244                           | first 2/0/0; repeat 0/0/0         |
| Empty     | 54, 365, 311                    | 262, 277, 232                          | 246, 264, 219                           | first 0/0/0; repeat 0/0/0         |

In **all six** clean runs, the largest early task started 2–11 ms after Chromium's `RemoteFontLoaded` event for Veneer. Each trace has roughly 926–927 `LayoutInvalidationTracking` events with reason `Fonts changed` across the three loaded faces; these are trace events, not a count of distinct elements. The largest layouts mark 318 of 319 layout objects dirty. Inter, Veneer and Bebas Neue finished in that order. This directly implicates the cold `font-display: swap` face change in local main-thread work during the first swipe, but does not establish the delay seen in Messenger. Veneer and Inter are already preloaded at High priority; the previous font review retained `swap` to keep the branded face in the persistent shell. Changing to `optional` could leave a cold session in a fallback face, and another preload could compete with the current critical assets. [Web font guidance](https://web.dev/learn/performance/optimize-web-fonts) describes those trade-offs. No brand-font, hero or media product source was changed on this evidence alone. One populated settled-first run had a 71 ms timer task with about 1.5 ms of script and a 54 ms event task with about 15 ms in AppShellRoot; neither repeated in the other five runs or in repeat scrolling.

The settled [no-swipe control](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/menu-none-0-clean.json) and four [post-swipe 0 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/menu-swipe-0-clean.json), [250 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/menu-swipe-250-clean.json), [750 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/menu-swipe-750-clean.json), and [1,500 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/menu-swipe-1500-clean.json) conditions each retain five fresh runs with source hash `5f249ab6352c`:

| Menu condition   | Browser `click` | Menu opened | Actual touch-end to pointerdown |
| ---------------- | --------------- | ----------- | ------------------------------- |
| No swipe         | 5/5             | 5/5         | not applicable                  |
| Swipe + 0 ms     | 5/5             | 5/5         | 67–69 ms                        |
| Swipe + 250 ms   | 5/5             | 5/5         | 316–317 ms                      |
| Swipe + 750 ms   | 4/5             | 4/5         | 815–819 ms                      |
| Swipe + 1,500 ms | 2/5             | 2/5         | 1,566–1,569 ms                  |

The four misses in the last two conditions still had pointerdown/up on Menu, but **no browser-dispatched `click`** and no scroll events in the preceding 200 ms. Thus the earlier hypothesis that misses occur only during scroll momentum is disproved by the clean runs. An [80 ms held CDP touch at 0 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/menu-held-0.json) clicked/opened 4/5; the [held 1,500 ms touch](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/menu-held-1500.json) clicked/opened 5/5. The held samples use source hash `6a57880707b8`. Every Menu failure across these retained conditions lacked a click, so none demonstrates a shell click-handler failure. Results vary by run and input method; no pointerup-based activation workaround was added.

The hero fallback was tested with [three normal](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/home-empty-hero-build.json) and [three forced unsupported scroll-timeline](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/home-empty-hero-forced.json) runs sharing source hash `6138f3486c74`. The forced arm reports `CSS.supports('animation-timeline: scroll()') === false` and the injected fallback CSS. Both arms had zero settled first/repeat ≥50 ms tasks. At 0, 150, 300 and 500 px of scroll, the media/veil opacities matched within 0.00003. One forced repeat had a 33.3 ms frame-interval p95; the other five repeat samples were approximately 16.8 ms. No repeatable fallback cost or visual difference justified a product change. The forced mode is a local capability simulation, not a physical older WebView.

The installed Android 16 emulator started, Chrome was present, and `adb reverse` bound the Local preview. Automatic approval review rejected `adb shell am start` to open the page, stating only `blocked by policy`; the emulator was stopped without a page-behavior result. No UAT or PRD release or physical Messenger comparison was made. The reported Messenger delay remains open, with the previously identified cold font-swap work now a concrete local contributor to investigate under release acceptance.

### Final source-bound rerun

After formatting and `pnpm build:web`, the final [populated Home](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-home-populated.json), [empty Home](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-home-empty.json), five [no-swipe Menu controls](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-menu-none-0.json), [swipe + 0 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-menu-swipe-0.json), [250 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-menu-swipe-250.json), [750 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-menu-swipe-750.json), [1,500 ms](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-menu-swipe-1500.json), and [forced hero fallback](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-hero-forced.json) all share source hash `4e9c2c86a541`, product build hash `d62bbb967245`, and `treeUnchanged: true`. Each of the six font-adjacent tasks starts 1–10 ms after `RemoteFontLoaded` for Veneer; all six traces record 926–951 `Fonts changed` layout-invalidation events across loaded faces. The font-adjacent task is the largest early task in five runs. Populated run 1 additionally contains a **406 ms** task, with **364 ms** of Layout, starting **930 ms after the Menu-tap request**. Its layout marks 99 of 445 objects dirty, rather than the near-whole-document 318 of 319 objects in the font-swap task. That later outlier must not be counted as first-swipe work. The first `scroll` event and the following rAF callback remain event/callback timestamps, not a measured visible frame.

The final populated settled first-traversal traces have 0/8/0 tasks ≥50 ms and repeat traces 0/0/0. The eight-task outlier includes 161 ms `Commit`/`Layerize`, 159 ms `EventDispatch` with about 3 ms of AppShellRoot `FunctionCall`, and 115 ms `HitTest`; it does not show recurring motto drawing. Final empty normal first traversal has 1/1/2 tasks ≥50 ms and repeat 0/0/1. These outliers reinforce that a zero-long-task claim for all scrolling would be unsupported. A separate cold Menu attempt in populated run 1 opened after 1,765 ms, while other cold Menu attempts failed; this mixed early-input scenario does not isolate shell activation cost.

All four misses still had Menu pointerup and **no browser `click`**. The two 0 ms misses had three scroll events in the preceding 200 ms; the 750 and 1,500 ms misses had zero. Thus neither ongoing momentum nor a shell click handler failure explains every miss. The earlier five-run series had different per-delay success counts, so the synthetic tap result is variable and cannot establish Messenger tap behavior. No `pointerup` workaround was made.

The [normal hero arm](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-home-empty.json) reported scroll-timeline support; the forced arm reported it unsupported and applied fallback CSS. At 0/150/300/500 px, media/veil opacity differed by at most 0.000024. Forced fallback first/repeat traversals had 0/0/0 ≥50 ms tasks; the normal arm had the outliers listed above. Forced repeat frame-interval p95 was 16.8/33.3/16.8 ms. This does not identify a repeatable fallback-path slowdown. The forced document interception changes load conditions, so cold-load timings are not compared across hero arms.

No follow-up product source change was justified: the font swap is attributable to cold layout, but Veneer and Inter are already preloaded, and replacing branded `font-display: swap` with `optional` could leave the persistent shell in fallback type for the session. The Menu misses occur before browser click dispatch, and the fallback hero retains opacity and settled behavior. The diagnostic harness and report changed; the current animation, typography, native scrolling, player behavior, and navigation code remain as previously implemented. Final local checks passed: [validation log](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-validation-after-report.log), [build log](../../../.codex-artifacts/runtime-performance/2026-10-10-messenger-followup/final-build.log), strict OpenSpec validation, `pnpm agent:check`, focused performance-helper tests, and `git diff --check`. `graphify update .` completed. The emulator and same-phone Messenger/Chrome release checks remain open for the reasons above.
