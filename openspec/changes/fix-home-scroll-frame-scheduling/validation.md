# Home scroll scheduling repair

## Scope and source

The owner reports severe Home-only scrolling lag in Facebook Messenger and explicitly assigns implementation to Codex, with local commit, UAT delivery and later PRD promotion authorized. Baseline main is `416ef61f08472c3d70b66c986655cbc41fef33be`. Product changes are confined to the app-shell hero scroll connector; the approved fixed ghost, CSS opacity path, videos, typography, content and commerce are preserved.

The confirmed defect was direct event-time execution of the hero fallback despite the existing frame-batching contract. Scroll events now queue the existing single frame; resize invalidates geometry separately, and cleanup cancels pending scroll work. This establishes the scheduling repair, not a reproduced physical Messenger root cause.

## Focused regression

Four new cases failed against the original connector and passed after the patch: a scroll burst seeks the latest position once at frame time, scroll-before-resize and resize-before-scroll each retain one remeasurement, and disconnect cancels scroll work queued after initialization. Ordinary scrolling keeps the cached geometry. Existing threshold, fallback, hero replacement and off-Home cases also pass.

`pnpm test apps/web/src/components/app-shell/dom/shell-hero-scroll-progress.test.ts` passed app-shell, web-layouts and web-pages. Before/after logs are `.codex-artifacts/messenger-home-scroll/regression-before.log` and `regression-after.log`. `pnpm build:web` passed on the baseline and patched tree, including route isolation, asset checks and bundle budgets; the final build log is `.codex-artifacts/messenger-home-scroll/build-after.log`.

## Persistent Android freezes: Local diagnosis

The owner reports release 614 still freezes repeatedly throughout Home on a Pixel 6a running Android 17, including after 15 seconds of settling. The original scheduling repair did not resolve that field report. This follow-up is authorized for Codex implementation and UAT only; physical Messenger acceptance remains pending.

The useful engine target is Android's Chromium-based embedded WebView, whose rendering and GPU services participate in the embedding application rather than a desktop Chrome window. [Chromium's WebView architecture](https://chromium.googlesource.com/chromium/src/+/main/android_webview/docs/architecture.md) documents that distinction. [Meta's Chromium WebView article](https://engineering.fb.com/2022/09/30/android/launching-a-new-chromium-based-webview-for-android/) describes Facebook on Android, not the owner's particular Messenger binary. No primary source or device evidence establishes that binary's exact fork/version; do not claim it was identified or emulate it merely by changing a user-agent string.

No physical device was attached. The installed `Medium_Phone_API_36.1` AVD supplies Android 16, actual Google WebView `151.0.7922.199`, 411×914 CSS pixels at DPR 2.625, 1080×2400 native pixels, three virtual CPUs and 2 GB RAM. Its source/build helper remain under `.codex-artifacts/messenger-webview-20261017/`. This is an Android WebView control, not the Pixel 6a's GPU, Android 17 or Messenger.

The repair uses `clip` for both boxes, retaining their visual crop without adding nested scroll nodes around the fixed ghost.
