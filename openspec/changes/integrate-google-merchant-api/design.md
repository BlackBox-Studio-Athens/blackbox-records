# Design

## Context

Accepted publication owns public product content. Checkout's offer reader combines stock, availability, price and catalog reconciliation. Merchant Center has no configured product source. Google requires an API source, authorization and periodic product refresh. Its standard 2–7 day delivery policy does not describe pre-orders.

## Goals / Non-Goals

Use existing staff publication, price and stock workflows and keep synchronization outside the checkout critical path. Do not add shopper or staff UI, expose credentials, publish drafts, or activate ads.

## Decisions

Owner approved the final design and local implementation on 2026-10-27, including in-stock-only scope, removal/reinsertion, the simple rotating scan, account separation and the mapping rules below. On 2026-10-28, the owner authorized the isolated Google test-account pilot and required setup. On 2026-10-29, the owner authorized production setup, the combined release, activation and necessary verification, then requested full completion. Paid ads and conversion tracking remain excluded. The validation record separates this authorization from actual release and runtime acceptance.

- Reconcile from accepted publication and the authoritative offer reader, rather than copying draft CMS data or using Stripe alone. Stable variant identities identify submitted offers.
- Use one Google Cloud project, a genuine Google test Merchant account for UAT, and the existing production Merchant account for PRD. Each account has its own API source and service-account credential in environment-specific Worker secrets. Do not grant the UAT identity access to PRD. Register the project through the verified production account with an authorized admin and human developer contact. Default synchronization off. Separate sources in one Merchant account alone do not isolate product identities.
- Use a rotating scan of at most five candidate identities every fifteen minutes in UAT and PRD, reusing the existing schedule. PRD's five-minute trigger must not cause additional Merchant runs. Persist a scan cursor and per-offer last-success state; prevent overlapping claims. Do not add event hooks, a separate change detector, a queue, a cron or automatic Google status polling.
- Scan the union of accepted identities and previously managed identities so withdrawals remain discoverable. Count removals and refreshes within the same five-candidate limit. Use fair rotation so a failed item cannot stall the catalog. Recheck current facts on later attempts rather than replaying obsolete payloads.
- Submit only changed verified inputs, verified removals and unchanged eligible inputs whose last successful submission is seven days old. Record success only after provider acceptance; repeating an uncertain write uses the same stable identity. Do not refresh unverifiable last-good facts.
- Disable immediate provider retries for this job only, apply bounded request timeouts, and retry on later scan passes. Authentication and quota failures stop affected provider work rather than multiplying requests. Preserve paid-order delivery priority. Measure D1 rows, storage operations, actual network attempts including authentication, and CPU before activation; account allowances and normal-service headroom remain release gates.
- A quota failure conservatively defers the source until the next Google daily reset at 12:00 UTC, including minute-limit errors. Recovery requires one bounded complete quota read before writes; unknown or exhausted evidence keeps recovery blocked. Long variant IDs map deterministically to `bb_` plus the base64url SHA-256 digest to fit Google's 50-character offer-ID limit; the ledger retains the full application identity.
- Treat failed or incomplete source reads as uncertainty, never evidence of withdrawal. Absence-based removal requires a complete validated accepted inventory and a stable publication pointer. A successful current read that proves non-buyability permits removal of that managed offer. Missing price alone does not establish the reason. Reinsert the same variant identity when it is eligible again.
- Exclude all pre-orders and backorders for this initial integration. Require the raw persisted stock pre-order to be null (`preorderStartedAt IS NULL`), in addition to current authoritative buyability. Do not use `deriveShopperPreorder` or `isPreorderOpen` as the exclusion gate: an exact date can hide the shopper pre-order while the stored pre-order remains. Missing, malformed or unreadable stock is uncertainty, not eligibility. Preserve checkout and shopper date behavior.
- Clear a stored pre-order only through the existing stock operation after physical arrival is confirmed, never automatically in Merchant synchronization. Existing Copies arrived handles open pre-orders. For elapsed exact-date pre-orders, that button is hidden; the existing authenticated pre-order API can clear the state with `shipEstimate: null` and the current expected stock revision. Document this occasional operator recovery; do not add UI or direct database writes. Until cleared, such offers remain excluded even when the website permits purchase. Reconcile physical/online stock through the existing workflow before the offer is considered ready.
- Keep product identity separate from manufacturer identifiers: use the stable variant ID as Google's offer ID, never as a GTIN or MPN. The current schema has no typed GTIN/MPN fields. Omit unavailable or unverified GTIN, MPN and brand values; do not infer them from catalog number, `artist_or_label`, generic product-safety identifiers, retailer identity or existing presentation metadata. Include correct identifiers only when their meaning and exact physical variant are verified in an authoritative maintained source. Add no separate Merchant catalog, enrichment service or identifier editor for this initial integration.
- Omit `identifierExists` initially. Missing schema fields do not prove that the manufacturer assigned no identifiers. Missing identifiers do not automatically suppress an otherwise verified in-stock input; actual Google diagnostics determine serving eligibility. Do not assert `condition: NEW` from stock alone; any condition supplied must be verified, and used/refurbished products require their actual condition before submission. A new-stock assumption must be verified for the pilot rather than silently inferred.
- Use Google Merchant Center for diagnostics initially. A staff dashboard can be added later if real operating experience requires it.

## Risks / Trade-offs

Final-review corrections approved on 2026-10-27: scan cadence uses fixed UTC fifteen-minute clock slots (00/15/30/45), based on the current claim time, rather than fifteen minutes after the previous delayed start. Missed slots are not replayed. Leases still use actual elapsed time and quota cooldowns retain their exact reset deadline. Merchant requests strict checkout-flag evaluation details; a thrown error or error result preserves managed listings, while a verified closure permits removal. Existing shopper reads retain their safe fallback.

- Production readiness on 2026-10-29 reduced the implementation cap to two, within the approved maximum of five. A complete five-offer invocation requires 88 D1 queries, exceeding Free's 50; two require 37, with a conservative 39-call recovery bound. A healthy scan takes `ceil(candidateCount / 2) * 15 minutes`: 100 identities take about 12.5 hours, plus failures and Google processing. Freshness and lease checks remain intact.
- The implemented ceiling is 192 candidate checks per day. A stocked candidate normally causes one Stripe price request, or two for a legacy mapping without a Product ID. Google mutations occur only for changes, removals and weekly refreshes. These are source-level estimates, not measured hosted usage.
- Merchant API and account configuration can reject otherwise valid data. Test against a separate Google test account before activation, then verify processed product status.
- The existing offer reader intentionally returns no price for sold-out and catalog-drift states. Reconciliation must distinguish a verified withdrawal or sold-out state from a failed read; it cannot assume a missing price is a valid out-of-stock Google offer.
- Quantity-based shipping may differ from Google product-level estimates. Verify single and multi-item presentation before enabling free listings.
- Google return policy fields cannot fully express the sealed-recording exception. Do not attest to a mismatched policy; retain the site's full terms and resolve the Google policy separately.
- Identifier omission can reduce visibility or cause Google disapproval; successful submission is not proof of listing eligibility. If real diagnostics require missing data, resolve only the affected products through their owning catalog workflow. A later field/UI change requires its own approved scope and Claude handoff.

## Evidence for mapping decisions

- `apps/backend/src/domain/commerce/preorder.ts:54` preserves a raw pre-order while `deriveShopperPreorder` can return null after its exact date. `application/commerce/stock/set-stock-preorder.ts` accepts explicit clearing, and `infrastructure/persistence/prisma/d1-operator-stock-repository.ts` clears all stored pre-order columns with revision checking. `apps/staff/src/components/stock/PreorderControl.tsx:188` shows Copies arrived only for an open pre-order.
- [Google unique-product-identifier guidance](https://support.google.com/merchants/answer/160161?hl=en) instructs merchants to leave unavailable identifiers blank rather than invent values. [Identifier exists](https://support.google.com/merchants/answer/6324478?hl=en) does not allow inferring absence from missing local data. [Condition](https://support.google.com/merchants/answer/6324469?hl=en) distinguishes new from used/refurbished requirements. These rules were reviewed on 2026-10-27.

## Migration Plan

Physical condition authoring is required for selected physical publication, rather than for reading historical snapshots or saving incomplete drafts. The shared pure predicate treats Distro as physical and Release as physical when a nonblank format is not Digital or an existing StoreItem identity binds it to the physical catalog. Review, initial acceptance (including requests without a reviewed baseline), and retained execution enforce explicit New/Used. CMS validation reuses catalog identities without querying stock or prices. The existing Staff editors and Add to catalog must capture the same field; the owner retains Claude ownership of those UI changes. Unbound digital-only/editorial Release publication stays optional. The two preserved private pre-order drafts must pass normal condition-aware publication before their raw pre-order state is cleared.

After final design and implementation approval, implement and validate locally with provider fakes. Prepare isolated credentials and API data sources under their setup authorization, without committing secrets. Run an authorized bounded test-account pilot for submission, processing, removal/reinsertion, stock, price and pre-order exclusion. Genuine test accounts do not serve products; inspect their actual processing and issue statuses rather than assuming approval. The recorded synthetic fixture was disapproved, and neither accepted input nor a test-account status proves live policy eligibility or displayed shipping. Production promotion, product mutation and live listing activation retain separate readiness gates under the owner's current authorization. Disable synchronization to stop new API writes; reconcile or remove existing Google listings separately if rollback requires it.
