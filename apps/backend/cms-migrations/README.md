# CMS application migrations

These migrations belong to application-owned tables in `CMS_DB`. They are separate from EmDash's core migration manifest and from commerce's Prisma/D1 migrations. Never apply them to `COMMERCE_DB`.

Release bundles retain each built Worker's EmDash manifest as `migrations.json`. The core migration runner accepts `--manifest <path>` alongside `--wrangler-config <path>` so fresh deployment runners use the verified candidate's manifest, without rebuilding or depending on ignored Local files.

Check pending Local migrations with `pnpm --filter @blackbox/backend cms:application-migrations:local`. Add `--apply` to apply them through Wrangler's native Local migration runner. The default check reads existing history without creating application tables. History lives in `_blackbox_app_migrations`, separate from EmDash core migrations.

The command defaults to the canonical Local CMS database and `.wrangler/state`; `--persist-to <directory>` selects isolated Local state for testing. Hosted targets use `--env uat|prd`; PRD apply additionally requires one-run `--confirm-live-cms-changes`. The Local stack runs application migrations before starting the CMS. The compiled CMS smoke applies and replays migrations against temporary Local state, then verifies publication creation and status reads. Request-time application migration is not configured.

The application migration command also reports native EmDash fields that still require publication-complete values. With `--apply`, it idempotently changes only the approved editorial collections' `required` flags to false. Brand-new databases receive this configuration from the generated seed. The draft hook continues to enforce safety and supplied references; every publication path enforces completeness. Run schema changes before deploying/restarting the CMS so cached schemas are fresh. Hosted application and schema changes require the same Free-tier preflight and PRD one-run confirmation as other migrations.

## EmDash 0.40.1 upgrade

Run the application migration **before** EmDash core migrations or the first upgraded runtime starts. Its `calendarDateFieldsToUpdate` report identifies `releases.release_date`, `distro.release_date`, and `news.date` still declared as `datetime`. Apply changes only those field types to `string`, preserving `YYYY-MM-DD` content and revision values. The generated seed uses strings for new databases; shared editorial validation still rejects invalid dates. This must precede core migration `079_datetime_normalization`, which otherwise normalizes datetime content and revision snapshots into UTC instants.

For hosted rollout, retain a verified database/media backup, apply the reviewed application migration, then check the new artifact's core manifest with `cms:migrations --env uat|prd`. Apply only with the exact `target.fingerprint` from that report. The release workflow checks and applies pending UAT core migrations before deploying either Worker; PRD applies remain inside the explicitly confirmed promotion job and require `--confirm-live-cms-changes`. A failed or unknown migration report stops deployment. Runtime mode remains `check` for hosted environments; Local uses `auto`. Do not downgrade code against migrated data as a rollback strategy.

EmDash now locks D1 core migrations. If a cancelled run leaves a lock, inspect it with the EmDash CLI's `migrate --status` using the same target/manifest options. Confirm no migration process remains before explicitly releasing that exact lock with `--release-lock <id>`. Never auto-release it or reset migration history. See [upstream recovery instructions](https://docs.emdashcms.com/deployment/core-migrations/#release-a-stuck-migration-lock).

The dependency patch retains revision-fenced deletes and concurrent draft-save protection absent upstream in 0.40.1. `test:emdash` must pass before replacing or removing it. The integration fixture now uses upstream's injected OpenAPI route.

After building the Local CMS, run `pnpm --filter @blackbox/backend test:cms-upgrade --source-state <stopped-0.38-state-directory>` against a stopped Local store or its backup. The command copies D1/R2 into disposable storage, checks migration and restart preserve dates, revisions, stock, prices and the accepted pointer, then removes only its copy. Omitting `--source-state` copies the canonical Local store, which must still be on 0.38 and stopped. After restoring the Local stack, `test:cms-publication` and `test:cms-preview` run the existing publication and Chromium/Firefox preview acceptance workflows.

Useful upstream changes include atomic D1 revision restore, media-reference cleanup protection, image/gallery seed fixes, and reduced D1 work. Our custom staff workspace and accepted snapshots remain authoritative. Blocks fields, site transfer, bulk tagging and broader plugin permissions are not enabled by this upgrade. Future blocks adoption must satisfy upstream's all-runtime compatibility rollout first. New hosted EmDash setup requires an explicit `siteUrl`, `EMDASH_SITE_URL`, or `SITE_URL`; our existing custom-auth workspace does not expose setup. MCP `media_upload` now takes bytes as base64 rather than a remote URL, and `media_create` can confirm signed uploads; neither endpoint is enabled here.
