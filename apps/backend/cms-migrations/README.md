# CMS application migrations

Artist activity uses optional native boolean `artists.is_active`, prepared idempotently by the existing catalog-schema command. Missing/null legacy values mean active, and native 0/1 normalize to false/true. Preparation changes no content or revisions. After the matching release, set Chronoboros inactive and confirm Sidus active through the normal Artist review/publication flow; repository fixtures do not update populated CMS stores.

The application migration runner adds nullable `releases.release_stage` text and `releases.gallery` JSON columns with native field metadata in one D1 batch, only when missing. This runs in the existing Local/UAT/PRD release flow and leaves content, drafts, revisions, media and publication pointers unchanged. Fresh seeds and the explicit catalog-schema setup define the same fields. Missing/null stage values retain the legacy date-based interpretation; gallery remains optional.

These migrations belong to application-owned tables in `CMS_DB`. They are separate from EmDash's core migration manifest and from commerce's Prisma/D1 migrations. Never apply them to `COMMERCE_DB`.

Release bundles retain each built Worker's EmDash manifest as `migrations.json`. The core migration runner accepts `--manifest <path>` alongside `--wrangler-config <path>` so fresh deployment runners use the verified candidate's manifest, without rebuilding or depending on ignored Local files.

Check pending Local migrations with `pnpm --filter @blackbox/backend cms:application-migrations:local`. Add `--apply` to apply them through Wrangler's native Local migration runner. The default check reads existing history without creating application tables. History lives in `_blackbox_app_migrations`, separate from EmDash core migrations.

The command defaults to the canonical Local CMS database and `.wrangler/state`; `--persist-to <directory>` selects isolated Local state for testing. Hosted targets use `--env uat|prd`; PRD apply additionally requires one-run `--confirm-live-cms-changes`. The Local stack runs application migrations before starting the CMS. The compiled CMS smoke applies and replays migrations against temporary Local state, then verifies publication creation and status reads. Request-time application migration is not configured.

Native catalog fields (for example News Artist, Release tracklist, singles and clips) are added by `prepareCatalogSchema` through EmDash's SchemaRegistry, not by SQL files. `pnpm --filter @blackbox/backend cms:catalog-schema --env local|uat|prd` runs it idempotently against the target `CMS_DB`; PRD requires one-run `--confirm-live-cms-changes`. Both release sequences run it after EmDash core migrations and before deploying the CMS, so a new field in that function reaches UAT with the next release and PRD with the next confirmed promotion. It changes schema only, never content.

The application migration command also reports native EmDash fields that still require publication-complete values. With `--apply`, it idempotently changes only the approved editorial collections' `required` flags to false. Brand-new databases receive this configuration from the generated seed. The draft hook continues to enforce safety and supplied references; every publication path enforces completeness. Run schema changes before deploying/restarting the CMS so cached schemas are fresh. Hosted application and schema changes require the same Free-tier preflight and PRD one-run confirmation as other migrations.

## EmDash 0.41.0 upgrade guidance for older environments

Run the application migration **before** EmDash core migrations or the first upgraded runtime starts. Its `calendarDateFieldsToUpdate` report identifies `releases.release_date`, `distro.release_date`, and `news.date` still declared as `datetime`. Apply changes only those field types to `string`, preserving `YYYY-MM-DD` content and revision values. The generated seed uses strings for new databases; shared editorial validation still rejects invalid dates. This must precede core migration `079_datetime_normalization`, which otherwise normalizes datetime content and revision snapshots into UTC instants.

For hosted rollout, retain a verified database/media backup, apply the reviewed application migration, then check the new artifact's core manifest with `cms:migrations --env uat|prd`. Apply only with the exact `target.fingerprint` from that report. The release workflow checks and applies pending UAT core migrations before deploying either Worker; PRD applies remain inside the explicitly confirmed promotion job and require `--confirm-live-cms-changes`. A failed or unknown migration report stops deployment. Runtime mode remains `check` for hosted environments; Local uses `auto`. Do not downgrade code against migrated data as a rollback strategy.

EmDash now locks D1 core migrations. If a cancelled run leaves a lock, inspect it with the EmDash CLI's `migrate --status` using the same target/manifest options. Confirm no migration process remains before explicitly releasing that exact lock with `--release-lock <id>`. Never auto-release it or reset migration history. See [upstream recovery instructions](https://docs.emdashcms.com/deployment/core-migrations/#release-a-stuck-migration-lock).

The calendar-date conversion above applies to environments upgrading from versions before core migration `079_datetime_normalization`. Keep this guidance for those older environments.

Version 0.41.0 adds core migrations `086_relations_structural` and `087_reference_field_relations`. They consolidate relation schemas and migrate eligible legacy reference fields to relation edges while preserving legacy columns. Retain the pre-upgrade backup and verify related Artist/Release reads and publication before any hosted rollout. Do not deploy older code against the upgraded schema.

## EmDash 1.0.1 upgrade

The retained 1.0.1 notes below describe the older migration path. Current EmDash 1.1.0 builds add core `090_redirect_enable_loop_guard` and `091_redirect_artifacts`, plus any missing earlier migrations from each target's actual history. Generate a fresh manifest for each environment; do not reuse another environment's check fingerprint. Keep Access authentication, disabled sessions/update checks and D1/R2 bindings unchanged. The core patch still protects revision-fenced deletion and draft-save races; the scoped admin patch routes native image uploads through the thumbnail-producing uploader.

For 1.1.0 acceptance, run `test:cms-upgrade --source-history current --source-state <stopped-1.0.1-store>` and `test:cms-upgrade --source-history legacy --source-state <retained-older-store>`. Both paths use disposable D1/R2 copies and verify two starts, preserved revisions, dates, relationships, media, publication pointers, prices and stock. The older path also verifies missing seed completion and one-shot timestamp normalization. Omit `--source-state` only when the canonical Local store is stopped. Application `0005_publication_history.sql` adds nullable comparison evidence and the calendar index without inventing legacy baselines or completion times.

Build a fresh CMS artifact and use its generated migration manifest for core migration checks and applies. EmDash 1.0.1 moved internal executor paths, so a manifest from an earlier build is not valid for the upgraded runtime. Preserve the existing application-before-core migration order. Hosted core migrations still require checking the candidate manifest and applying with the exact `target.fingerprint` from the check report.

Core migration `088_cron_oneshot_utc` canonicalizes one-shot task timestamps while preserving their instants. Migration `089_auto_seed_completion` marks configured existing sites as seeded; it does not recreate content that was removed. Keep the 079 calendar-date guidance and 086/087 relation guidance above for environments that have not yet crossed those migration boundaries.

Both atomic revision-fenced deletion and the concurrent draft-save race fix remain absent upstream in 1.0.1, so retain the dependency patch. Keep `test:emdash` passing before replacing or removing the patch; the integration fixture uses upstream's injected OpenAPI route.

Hosted upgrades require a Cloudflare budget review, verified CMS database and media backup, and a target migration-history check. For a confirmed 0.41.0 target already through 087, the only pending migrations are 088/089: 088 updates timestamps only when their original value still matches, and 089 inserts the seed marker only when absent. Neither rewrites editorial content, so this path does not require an editorial pause. Reassess older or unexpected histories before applying. Accept the upgrade in UAT before separately approved PRD code promotion. Do not change catalog, prices, stock or shopper launch as part of this upgrade. Never downgrade code against migrated data. The upgrade adds no KV bindings or sessions, and custom Access authentication remains unchanged.

After building the Local CMS 1.0.1 artifact, run `pnpm --filter @blackbox/backend test:cms-upgrade --source-state <stopped-local-state-directory>` against a stopped pre-0.42 Local store or its backup. The command copies D1/R2 into disposable storage, creates a pending Release draft with gallery media and disabled scheduling fixtures, and removes a collection from the seed namespace in that copy. It verifies migrations 088/089 and two starts preserve drafts, dates, revisions, media, existing relation edges, stock, prices and the accepted pointer without recreating the missing collection. It accepts initialized 0.38–0.41 stores and checks calendar conversion only when still pending; already-migrated stores cannot prove the migration and are rejected. Omitting `--source-state` copies the canonical Local store, which must be stopped. After restoring the Local stack, `test:cms-publication` and `test:cms-preview` run the existing publication and Chromium/Firefox preview acceptance workflows.

Useful upstream changes include atomic D1 revision restore, media-reference cleanup protection, image/gallery seed fixes, and reduced D1 work. Our custom staff workspace and accepted snapshots remain authoritative. Blocks fields, site transfer, bulk tagging and broader plugin permissions are not enabled by this upgrade. Future blocks adoption must satisfy upstream's all-runtime compatibility rollout first. New hosted EmDash setup requires an explicit `siteUrl`, `EMDASH_SITE_URL`, or `SITE_URL`; our existing custom-auth workspace does not expose setup. MCP `media_upload` now takes bytes as base64 rather than a remote URL, and `media_create` can confirm signed uploads; neither endpoint is enabled here.
