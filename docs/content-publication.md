# Content publication

Publication history expands lazily to show publisher, destination, action, affected entries, requested/completed times and readable field comparisons. Comparisons use the retained snapshots on either side of the actual activation. Missing legacy evidence shows **Comparison unavailable**; adjacent journal rows never establish a baseline. Application migration `0005` retains the baseline hash and indexes successful calendar activity. Verified completion fills `completed_at` once, including recovered activation receipts.

The authenticated `/calendar/` is read-only. It shows every successful publication, including repeated updates and removals, in a desktop month view or phone agenda. Month, collection and view remain in the URL. Days use `Europe/Athens`, including daylight-saving changes. Known completion times determine the date; legacy requested times have an explicit label. Every month page is loaded, with retry and incomplete-results states. History keeps its existing pagination. Details and calendar APIs are environment-scoped and private/no-store; snapshots are read only when details open.

Use a reader-only UAT code release first, then the combined upgrade release after that reader is verified. Preserve the normal backup, Free-tier, target-specific manifest and migration fingerprint checks. PRD remains a separately approved immutable promotion. A database migration is recovered with the verified backup/forward-recovery procedure; never downgrade the running code against migrated data.

The staff workspace saves private drafts through EmDash's native content API. Review changes finishes autosave and opens an individual review inside the editor without replacing the grouped selection. `/review/` supports Select → Review → Publish for up to twenty entries. Discovery compares saved revisions with accepted content because native collection lists retain published field values; revision reads remain bounded by each page's scan limit. Publication completeness is checked separately at every publication and snapshot boundary. Linked catalog entries retain Selling's explicit activation operation; editorial-only releases need no price or stock.

Authenticated `POST /_emdash/api/blackbox/publication-review` reads exact saved revisions and the accepted snapshot. It returns readable comparison values, completeness issues, required unpublished references, protected image sources and a baseline identity. Reviews and combined previews create no revisions or publication operations. Preview resolves the selected entries together against accepted content; it never substitutes an unrelated newer draft. Required unpublished artists are included only by explicit staff action. Missing or incomplete dependencies block publication.

Reviewed requests retain the baseline identity alongside revisions. Acceptance, preparation and activation check that identity; a changed website or draft requires fresh review. Legacy retained requests without a baseline remain recoverable. The final Publish change/Publish N changes action sends directly. Preparing, Checking website and Confirming publication reflect backend stages; On the website requires public confirmation. Visual preview failure offers Retry or explicit Publish without preview, which does not bypass content, dependency, revision or server rendering checks.

History uses the retained journal through cursor-paginated `GET /_emdash/api/blackbox/publications/history`, optionally filtered by collection and record ID. The staff menu opens one right-side history panel with status badges, the requested Athens time and expandable publisher, destination, entry and failure details. New intents retain entry titles/types, publisher, request time and destination. Missing legacy metadata is identified as unavailable. History has no restoration or undo actions; `Discard saved changes` is a separate editor action for the current unpublished draft and never restores an arbitrary historical revision.

A durable CMS journal precedes native publication. Preparation replaces selected entries in the last accepted snapshot, copies only new media, validates the affected public templates, and conditionally activates the immutable R2 manifest. Unrelated drafts never enter the candidate. Each entry's website state is compared with the accepted snapshot, not inferred from global publication history. Pending operations check every two seconds for one minute and every thirty seconds thereafter, stopping after thirty minutes with Update not confirmed and Check status. Hidden/offline views pause reads. Stock remains authoritative for physical copies, online quantities and movement history.

The public renderer runs Astro inside a SQLite Durable Object. Pages serves compiled assets and forwards allowlisted public GET/HEAD requests with only `Accept` and optional `If-None-Match` through `PUBLIC_SITE`; cookies and authorization are never forwarded. Astro's resolved routes supply the release's allowlist, including dynamic routes. Other paths return a static `no-store` 404 without a renderer call. Every `/favicon*` asset and fingerprinted ESM image bypasses rendering and preserves its bytes. The renderer has R2 access only, with no D1, commerce secrets, sessions or KV. Private namespaces are blocked. Media URLs are `/media/content/<media-sha256>`: the renderer serves a media SHA only while the live snapshot or one of the three most recently accepted snapshots references it, so drafts, failed candidates and retired media stay private. A publication therefore keeps every unchanged image URL, its browser and edge cache entries and its Images transformations. Hosted CMS images use direct Images URLs with the configured canonical Pages source; Local and private preview images pass through. The legacy `/media/content/<snapshot-sha256>/<media-sha256>` shape stays readable for those same snapshots, so already-open pages keep their images. The pages.dev URLs, Local base path, checkout gates and holding branch remain unchanged.

The renderer checks the pointer at most once every five seconds per active object. Concurrent refreshes share one read, serving the current identity while it completes. The persisted SQLite cache keys include release, snapshot, origin and path; after a restart a cache hit reads the current R2 pointer without parsing the snapshot or rendering again. The cache uses byte-accounted LRU eviction at 8 MiB, with a 2 MiB entry ceiling including its key and headers, shared by published HTML and `/preorder-showcase.json`. This one editorial JSON route derives clips and artwork from the same accepted snapshot as the release page; pre-order status, prices and stock remain fresh Worker reads. Other JSON is not cached here. Selection retires rows outside the active release/snapshot identity once per identity change, and late retired renders cannot insert an old row. Query-bearing, cookie-setting and explicitly private or `no-store` responses are not persisted. Weak ETags support bodyless GET/HEAD 304 responses; HEAD 200 also omits the body. Successful eligible HTML and showcase JSON are `public, max-age=0, s-maxage=30, stale-while-revalidate=30`: Workers Caching may serve a response for up to 60 seconds, keyed by Worker version, while browsers revalidate every use. A shopper can therefore see previous content for about a minute after publication is confirmed. `/content-version.json`, `/release.json`, previews, not-found and error responses stay `no-store`, so confirmation itself is never cached. Versioned media is immutable. A transient pointer-read failure keeps the last selected in-memory identity. Cold starts without readable accepted content return 503. The site does not fall back to drafts. Sixty seconds is the normal-service p95 publication target, not an outage guarantee.

Runtime activation calls the private default renderer entrypoint through the existing service binding before public confirmation. It verifies and refreshes the exact active pointer in `public-v2`, retires earlier persisted responses, then purges publication-tagged HTML and showcase JSON from that entrypoint. A clip addition, replacement or removal therefore changes both response identities together. Refresh epochs prevent stale in-flight pointer reads from overwriting activation. Purge failures or lost receipts retain accepted content and keep the journal confirming for safe retries, including after the pre-activation retry limit. A retry preserves already rendered rows for that same active identity. Local alone can proceed if its emulator has no edge cache API; UAT/PRD require successful purge. The installed emulator cannot establish native purge propagation. The short response window stays until the authorized hosted pilot verifies it. Publication has no GitHub dispatch, CI claim or deployment-receipt path; the CMS Worker accepts only runtime publication. Its token-gated `publications/snapshot`, `media` and `catalog` GET routes stay read-only for release preparation.

`public-v2` serves public rendering and media; `publication-v2` handles private validation and previews. Both request the Eastern Europe location hint, which Cloudflare treats as best effort. The replaced `public` instance held only disposable in-memory caches: accepted manifests, pointers and CMS journals remain in their existing R2/CMS owners. Render buffering remains bounded at 4 MiB so read/render failures can produce an explicit 503 before any partial HTML reaches the client. Streaming would require a bounded tee, cancellation handling and a separate cache-write failure path; it is deferred under the change's simplicity condition.

## Recovery

Before storing or returning a buffered cacheable response, the renderer rechecks the accepted snapshot. A publication that retires an in-flight render makes that output `no-store`, removes its ETag, Last-Modified and cache tags, and prevents an old conditional 304 or cache insertion after purge. This check uses the existing selection and refresh interval; warm persisted hits still avoid SSR and manifest parsing.

### Distro withdrawal

Authorized operators can withdraw Distro through the existing `POST /_emdash/api/blackbox/publication-review` and `POST /_emdash/api/blackbox/content-publications` APIs with `action: "withdraw"`. Review supplies exact saved revisions and the accepted baseline; submission requires that baseline and a retained request UUID. Omitting action preserves normal publishing. Withdrawal review shows each accepted entry becoming absent, without publishing its private draft or requiring complete draft fields. Other collections cannot be withdrawn through this operation.

Withdrawal pauses new checkout before native unpublish, preserves private drafts and all stock, reservations, orders and provider bindings, and removes both Distro records and linked Store Item identities from the candidate snapshot. Public validation checks Store rendering and removed product/checkout routes returning 404. The publication journal retains pause and native-transition receipts; retries recover the same request and reject later edits. Rendering failure keeps the previous website active with checkout paused. Confirmation and cache timing follow normal publication. Each environment requires its own review, identities and request; software release never copies a withdrawal between environments.

The browser retains the request ID before sending it. Retrying an uncertain response returns the same request; conflicting reuse is rejected. The CMS arms its alarm before processing and resumes pending work after eviction. Retries back off from two seconds to a five-minute ceiling. Pre-activation failures retry up to six attempts and then preserve the previous public snapshot. Once activated, confirmation remains recoverable and cannot be reported as a preparation failure. Live requires the public origin's content identity to match. Investigate repeated service failures before manually retrying a failed request.

R2 manifests, media and the accepted pointer are durable. Code promotion consumes the reviewed paired renderer/CMS/gateway artifacts and keeps that pointer. Initial cutover bootstraps from the previously accepted snapshot identity. An older static deployment is not a content rollback: its content may be stale. Use a reviewed compatible code candidate; content rollback requires a separately selected, verified accepted snapshot.

## Free-tier operation budget

Showcase JSON adds at most one Pages gateway invocation and one public renderer invocation when the Home section reads it, alongside the independent narrowed commerce read. An edge miss adds one DO request; an unchanged persisted response uses one SQLite row lookup and its indexed LRU update, with no SSR or snapshot parse. Pointer refresh remains shared at the five-second interval, with one pointer read on wake and one manifest read when rendering accepted content. Retirement scans the byte-bounded cache and deletes older rows once per selected identity, including after a restart; a retry for the same in-memory identity adds no retirement scan. Insertion, eviction, row deletion and index writes consume shared storage allowances. The JSON shares the existing 8 MiB cache and 4 MiB render-buffer limit; it adds no binding or background work. Local tests cover these seams, not hosted request counts, purge propagation or account-wide allowance.

Owner: the existing BlackBox release workflow and CMS/public runtimes. Each environment adds one service-only public Worker and one SQLite Durable Object namespace. Existing R2 buckets and CMS D1 databases are reused. No paid plan, KV binding, queue or additional cron is introduced. CMS and public build wrappers reject KV in source and generated configuration.

Text-only publication normally uses one journal insert, a native revision transition, roughly ten journal reads/writes, one manifest write, one pointer write and one acceptance marker. Rendering validation is bounded to sixty-one distinct pages for a twenty-record batch. Confirmation and retries add bounded reads; image changes add one source read and immutable write per new image. History polling is read-only. Public HTML and original media consume Worker requests, and Durable Object requests on edge-cache misses; pointer reads are limited by the five-second interval, while media costs one R2 object read per uncached delivery. Direct Images delivery removes the browser's transformation proxy hop; a cold Images source fill can still call the media gateway/renderer. Media outside the live snapshot costs one acceptance-marker listing and at most three manifest reads once per renderer instance, not per request. The HTML cache is capped by bytes at 8 MiB. A cache hit reads one SQLite page row and updates its LRU position; insertion and eviction add bounded storage work. SQLite storage operations consume the account's shared Free allowances; they introduce no KV binding. These are application operation estimates; D1 billed rows include indexes and queries.

Release pilot ceiling: one UAT text publication, at most 100 public requests, 100 R2 writes, 1,000 R2 reads, 5,000 D1 rows written, 100,000 D1 rows read, and 100 GB-s additional DO duration. Reserve at least half of each Free allowance for ordinary service. Stop the pilot on any quota warning, unexpected write amplification or failure loop. Exhaustion returns an explicit pending/failure or public 503; it never enables billing or changes the accepted pointer to an incomplete candidate. Record account-wide usage and measured results in the change's release evidence before hosted work.

Pages service bindings use the API's `deployment_configs.production.services` field ([Cloudflare API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/methods/edit/)). The gateway binding is verified before upload. Deployments stay in `.github/workflows/pages.yml`; PRD consumes the accepted UAT candidate without rebuilding and does not authorize catalog mutation or checkout launch.
