# Merchant product synchronization

Owner: the backend commerce schedule. This integration sends accepted public, buyable, fixed-price EUR Store Items to Google for Greece free listings. It adds no staff or shopper interface. Publication, stock and price changes continue through their existing owners. The [Merchant change](../openspec/changes/integrate-google-merchant-api/design.md) owns scope and acceptance; [commerce operations](commerce-operations.md) owns physical stock and fulfillment.

## Configuration and activation gates

Synchronization is disabled by default. No Merchant account, data source, credential or enabled deployment configuration is created by this implementation. Local never runs the provider job. Credential setup, hosted migration/deployment, the UAT pilot, PRD product writes and live listing activation require their separate authorizations.

| Worker binding                  | Purpose                                                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `MERCHANT_SYNC_ENABLED`         | Only the exact value `true` enables UAT/PRD work. Leave absent or false until the target is accepted.             |
| `MERCHANT_ACCOUNT_ID`           | Numeric Merchant account ID for this environment.                                                                 |
| `MERCHANT_DATA_SOURCE_ID`       | Numeric primary API data-source ID in that account.                                                               |
| `MERCHANT_SERVICE_ACCOUNT_JSON` | Worker secret containing the service account's `client_email` and PKCS#8 `private_key`. Never commit or print it. |
| `PRD_MERCHANT_SYNC_APPROVED`    | PRD additionally requires the exact value `true`; enabling the general switch alone cannot authorize PRD writes.  |

Use one Google Cloud project with a genuine Google test Merchant account for UAT and the existing production account for PRD. Each account has its own API source and service-account identity; the UAT identity must have no PRD access. Sources within one Merchant account do not isolate product identities. Project registration uses the verified production account, an authorized admin and a human developer contact under the separate setup gate.

Before its first mutation in each active run, the adapter verifies the exact account and source. UAT requires `testAccount: true`; PRD requires a non-test account. The source must be primary `API`, country `GR` only, language `en`, feed label `GR`, non-local, with `FREE_LISTINGS` enabled and every other destination disabled. Mismatches stop provider work. These checks do not establish product approval, shipping accuracy or permission to serve listings.

Apply additive commerce migration [0040](../apps/backend/prisma/migrations/0040_merchant_sync.sql) through the approved release process before enabling a target. `MerchantSyncRun` stores its cursor, next-run time and lease. `MerchantManagedOffer` stores variant/slug ownership, the last accepted input hash and successful submission time. Both are scoped by environment, account and source; changing any of those starts a different ledger scope. Retain the previous scope until its remote listings have been separately reconciled or removed. Do not reset the ledger to recover a provider failure.

## Eligibility and timing

Only accepted snapshot identities and content are read. Each candidate is checked against the authoritative offer, current availability and hold-adjusted stock. Sold-out, non-buyable, pay-what-you-want and all stored pre-order/backorder offers are excluded; a previously managed excluded offer is removed and can later be inserted with the same variant identity. Missing/malformed stock, catalog drift, missing price without a verified reason, or unreadable accepted content is uncertainty, not permission to invent an offer or remove one.

The persisted pre-order must be explicitly clear, even after an exact date makes the shopper-facing pre-order disappear. Merchant synchronization never clears it. Confirm physical arrival first, then use Selling's existing **Copies arrived** and reconcile physical/online counts. If an elapsed exact date hides that button, an authorized operator can use the existing authenticated `PATCH /api/internal/variants/{variantId}/stock/preorder` operation with `shipEstimate: null` and the freshly read `expectedRevision`. A revision conflict requires a fresh read and reassessment. This is an occasional recovery through the stock API, not a direct D1 edit; it must not clear a delay before the copies arrive.

Google's offer ID is the stable variant ID when it fits the 50-character limit. Longer IDs become `bb_` plus the base64url SHA-256 digest of the complete variant ID (46 characters); insertion and removal use the same mapping while the ledger keeps the original ID. The product identity also includes `en` and `GR`. None of these IDs is a GTIN or MPN. Unknown GTIN, MPN, brand and `identifierExists` are omitted; catalog numbers, artists, retailer names and safety identifiers are not substituted. Condition is also omitted rather than asserted from stock alone. Verify the actual physical product condition and identifier requirements in the pilot. Used/refurbished stock needs its correct condition before submission; it must not pass under an assumed new-stock policy. Google can accept an input and still reject or limit the processed product. Use Merchant Center diagnostics; no status-polling job or new editor is added.

The existing schedule claims at most one run per fifteen-minute UTC clock slot per scope, with a ten-minute lease and at most five candidate identities. PRD's five-minute trigger cannot increase that scan rate. The sorted rotating union includes accepted and previously managed identities, so withdrawals remain discoverable and a failed item does not block later items. Changed inputs, verified removals and unchanged inputs last submitted at least seven days ago share the five-candidate limit. A complete healthy sweep takes approximately `ceil(candidate count / 5) × 15 minutes`; 100 candidates take about five hours, plus Google processing. Outages increase that delay.

## Failure and operator recovery

Cadence uses current UTC clock slots (00/15/30/45), not fifteen minutes after a delayed start. One run may claim each slot; missed slots are not replayed. A still-active lease or quota cooldown blocks the claim. Adjacent slots can start less than fifteen minutes apart after a delay, but the daily ceiling stays 96 passes.

Merchant reads checkout flags with evaluation details. A thrown provider error or returned error details are uncertainty and preserve existing managed offers. Verified closure still removes offers through normal rotation. Ordinary shopper checkout keeps its existing safe fallback.

Watch the redacted `merchant_sync_outcome` event in [Worker observability](worker-observability.md). It reports outcome, checked/upserted/removed/failed counts, duration and a safe reason, without credential or provider payloads. `durationMs` is elapsed runtime, not CPU or a billed operation count.

- `auth` and `invalid-source` stop remaining provider work for that pass. Resolve target access/configuration; disable the job during investigation to avoid repeated failed passes.
- `quota` additionally persists a cooldown until Google's next daily reset at 12:00 UTC. This conservatively also defers minute-limit errors. Before any resumed writes, one bounded quota read must establish a complete, non-exhausted result; unknown, paginated or exhausted evidence leaves recovery blocked. Google exposes daily usage and minute limits, not current minute usage. A quota recovery adds one quota request and ledger block/clear operations. No background quota polling is added.
- Timeout, network or individual provider errors retain ownership and last successful state and continue fair rotation. There are no immediate retries. Google requests and this job's Stripe reads use a three-second timeout; Stripe network retries are disabled only for this job. Google JSON responses are bounded to 64 KiB.
- Failed/incomplete inventory reads preserve remote products. Absence-based removal needs a complete validated accepted inventory and a stable publication pointer. Publication changes or lost leases stop mutations; later passes read current facts instead of replaying old inputs.
- A provider-accepted insert followed by a lost local success receipt remains tracked and can be removed or safely submitted again with the same identity. A missing remote product during removal is accepted as already removed. Do not manually replay old payloads.

Merchant runs are separate from paid-order delivery and cannot change checkout or publication results. Disabling `MERCHANT_SYNC_ENABLED` stops future Merchant writes; it does not withdraw products already on Google. Existing listings and rollback removal need separate, bounded reconciliation authorization. During a prolonged outage, last-good remote facts can become stale or expire: do not refresh them without current source verification.

For credential rotation, disable synchronization in the affected environment, replace that environment's Worker secret through the approved secret-management process, verify the identity/account/source in an authorized bounded run, then restore its accepted enablement controls and revoke the superseded key. Keep UAT and PRD access separate. Never place private keys, JWT assertions, access tokens, raw auth responses or secret-bearing commands in logs or evidence.

## Free-tier budget and pilot evidence

Reuse the existing commerce database, schedule and R2 accepted publication; add no cron, queue, KV or paid service. Follow the [Free-tier operating rule](cloudflare-free-tier.md) before any hosted pilot. The following are source-level estimates and limits, not measured Worker CPU, D1 billed rows, provider usage or hosted latency:

| Operation           | Source bound per environment/scope                                                                                                                                                                                                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Active scans        | At most 96/day; at most 480 candidate checks/day. PRD can also attempt the inexpensive claim on intervening five-minute triggers.                                                                                                                                                                                                   |
| Price reads         | Normally one Stripe price request per stocked candidate, or two for a legacy mapping without a Product ID: up to about 480/960 daily requests if every candidate needs that path. Include all attempts and failures.                                                                                                                |
| Google calls        | Zero if no mutation is due. A mutating pass normally needs one OAuth token exchange, two account/source verification reads, and at most five mutations: up to eight network attempts/pass, about 768/day at the continuous-write ceiling. No immediate retries or automatic status reads.                                           |
| Merchant D1 ledger  | One claim, managed-list read and finish per active pass, plus lease checks/ownership/success writes. Five successful upserts use up to 23 ledger statements; a skipped claim uses one. These are statements, not billed rows. Include existing offer, holds, stock, availability, catalog-reconciliation and index work separately. |
| Publication/storage | One accepted-snapshot load per active pass plus pointer checks during loading and before mutations. Ledger payload scales with managed identities; accepted and managed inventory reads each reject over 1,000 entries. Record actual snapshot bytes, stored rows/indexes and R2 reads.                                             |

Before activation, record current account-wide Worker, D1, R2, Stripe and Google usage/quotas and preserve at least half the affected Free allowance for ordinary service. Unknown allowance is not pilot approval. Bound the first authorized test-account pilot to five candidate identities and one mutating pass, with one separately authorized processed-status inspection. Measure actual network attempts including auth, D1 rows read/written, storage, Worker CPU and elapsed time, then revise the source estimates. Stop on a quota warning, unexplained amplification or a retry loop; do not upgrade the plan.

The Local D1 Worker regression measured 23 statements, 27 rows read and 18 rows written for five first submissions on 2026-10-27. This measurement covers the Merchant ledger with injected source/provider fakes; it excludes catalog, stock, hold and provider reads and does not establish hosted billing. The change's validation record links the source-bound result.

Record results and source fingerprints in the change's acceptance evidence. Test accounts approve products by default and do not serve them, so they do not prove production eligibility or displayed delivery. Before separate PRD listing activation, verify stock/price change, removal/reinsertion, pre-order exclusion, identifier/condition diagnostics, Greece BOX NOW coverage, the €3/€6/€10 quantity bands and the in-stock-only 2–7 working-day estimate against the website and checkout. Retain the complete website returns terms; do not attest to a Google return policy that loses the sealed-recording exception or faulty-goods remedies. The unsaved Google policy is not itself evidence of a universal listing block; inspect the actual account diagnostics.
